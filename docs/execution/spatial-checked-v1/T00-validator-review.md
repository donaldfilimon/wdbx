# T00 validator review

Read-only review of `tools/validate_wdbx_3d_evidence.py`, its eight unit-test methods, and T00 brief. No tests were rerun. Also read v5 master-plan §2.3 (lines 122–128) from the user-supplied package. This is a targeted review, not a claim of having reread that whole artifact. The forthcoming explicit first-packet `read_scope` allowance for v5 must validate its fixed required spans (1–624, 2511–2610, 2645–2725, 2766–2804) without inventing a full-document read. Full controlling-spec reads remain separate.

The validator correctly requires every named authority, immutable SHA-256, git identity or explicit external-artifact provenance, complete contiguous controlling-document read ranges, separate reported/executed evidence, and positive counts for executed tests. The CLI honestly labels acceptance as inventory admission without independently verifying content or execution. External user artifacts should retain null git commits and explicit provenance plus SHA-256; this exception is deliberate and should remain.

## Findings requiring attention before complete-inventory acceptance

1. **The v5 §2.3 required inventory is not fully represented.** The validator requires neither branch nor clean/dirty state; arbitrary `ref` is insufficient to distinguish those. Its required authority names do not require original command contracts, actual gateway schema, toolchain/lockfiles or current tests, all expressly named by §2.3. Add repository identity/state records and explicit scoped required inventory categories. File-content digest and immutable commit are already supported; external artifacts should not invent repository state.

2. **Noncontrolling rows bypass range typing entirely** (`validate_source_manifest`, lines 82–84). An additional source row can have missing, malformed, negative, out-of-bounds or string-valued read ranges and line counts and still be accepted. Partial coverage is legitimate, but its spans still need well-typed bounds and ordering. Add separate valid-partial and malformed-partial fixtures. Current malformed-type tests cover required authorities only.

3. **Executed evidence is structurally too weak for qualification admission** (lines 94–106). A nonempty artifact string can reference any path, with no immutable log digest, source/build identity, toolchain/target/feature tuple or explicit observation provenance. A row declaring `command: cargo check`, `kind: test`, `test_count: 4` passes the structural rule; even the existing reported/executed fixture uses that inconsistent command, although the reported evidence guard rejects it for a different reason. Inventory admission may deliberately preserve failed executions, so nonzero exit status must not be rejected wholesale. It needs an explicit qualification boundary: accepted inventory must never mean a positive executed-test claim is verified. Add a separate check-kind-with-positive-count negative fixture, positive executed-check fixture, and a failed-test record fixture. Pin immutable artifacts and source/build association before consuming any record as qualification.

4. **Repository-relative path check misses single backslashes and degenerate paths** (lines 71–74). The literal `'\\\\'` checks for two consecutive backslash characters. A single backslash, Windows drive spelling, `.` or a URI-like relative string can therefore pass. Execution artifact paths receive only a nonempty-string check. Use one common normalized relative-file-path policy, including artifact paths, and test single-backslash, traversal, drive, dot and URI spellings.

5. **Authority presence alone does not encode authority precedence or unresolved requirements** (lines 60–69, 107). Required names need only arbitrary nonempty repository/ref/owner/role strings; there is no structured inherited/reported/current authority relationship, dependency scope, unresolved-requirement status, or required source ownership/location mapping. Arbitrary extra keys, including unsupported qualification claims, are silently ignored. This is acceptable only if the audit document and consumers explicitly carry those constraints; the validator's contract should not imply that an empty error list proves the full T00 inventory is implementation-ready.

## Evidence boundaries

Synthetic all-authority fixtures with invented repeated hexadecimal identities exercise shape only. They do not establish actual source-byte provenance, completeness of the source audit or that controlling documents were read. The current distinction is valuable and should be retained in report wording. A complete real manifest must itself pass the validator; the execution packet's earlier `source-manifest.json` has `repositories`/`files` rather than the expected `schema`/`sources` envelope and is only a source hash inventory. The canonical T00 manifest path should be validated once authored, without treating that earlier inventory as its substitute.

The eight existing test methods cover the three named acceptance cases and several malformed inputs, but do not yet cover partial-row range types, duplicate authorities, bad execution artifact identity/path, checks mislabeled as tests, or a preserved failed execution. These are targeted admission gaps; this review makes no production-code or feature assessment.
